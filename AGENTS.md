# AIIDE Codex working rules

Use **minimum sufficient context**. After this file, read [codex/REPO-MAP.md](codex/REPO-MAP.md). Read [codex/CONTEXT.md](codex/CONTEXT.md) only when durable product or architecture context matters. Use headings or targeted sections of [PROJECT.md](PROJECT.md) only for roadmap, original intent, or broader decisions that the smaller files cannot answer. Treat `codex/archive/`, if created later, as cold history.

For a task, start with files the user names; otherwise use the repo map to choose a subsystem. Inspect directly relevant files and follow only necessary imports or call boundaries. Search for a specific symbol, command, selector, or path when ownership is unclear. Expand to a wider subsystem only when evidence requires it; whole-repository exploration is exceptional. An ordinary change often needs this file, the map, and roughly 3–8 relevant source files. That is a heuristic, not a cap. Stop investigating once implementation is safe.

Keep changes narrow. Do not refactor, rename, reformat, upgrade dependencies, revisit milestones, or audit adjacent UI/code merely because it is nearby. Cross the React/Rust boundary only when the task spans it. Preserve the trusted Rust/Tauri boundary: model tool arguments are untrusted, and repository access must remain project-relative, protected, and bounded. See `src-tauri/src/repository.rs` for current rules and limits.

Avoid generated/dependency output for application understanding: `node_modules/`, `dist/`, `.npm-cache/`, `src-tauri/target/`, and `src-tauri/gen/schemas/`. Avoid binaries, icons/assets, logs, lockfiles, and `*.tsbuildinfo` unless directly relevant. Before reading a large document, JSON/data file, or generated source, try headings, targeted search, or the needed line range. Do not inspect `.env`, `.env.*`, private keys, credentials, tokens, or local auth/config values by default; a safe example file such as `.env.example` may be read when relevant. Never print or copy secret values into context docs.

Validate progressively: focused check or unit test, affected compiler/type/lint check, then a broader build only when the change warrants it. Launch Tauri only for runtime behavior. For model/agent work, iterate with deterministic tests and run **one focused live Ollama pass near completion** when needed; one targeted follow-up after a finding is reasonable. After about two failures of the same runtime-dependent check, stop repeating it, isolate with deterministic evidence, and report what passed, what timed out, and whether direct connectivity works. Do not fix unrelated warnings.

This repository is currently in a read-only agent stage. Do not infer that editing, command execution, or Git mutations already exist. Use the current code rather than historical milestone notes as the source of implementation truth.
